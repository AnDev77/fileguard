# 구현 고려사항

실제 파일 업로드 과정에서 발생할 수 있는 보안, 데이터 정합성, 동시 요청, 운영 문제를 추가로 고려해 구현.

## 최소구현 수준 A, B 이외의 고려한 부분들.

### 1. 원본 파일명과 실제 저장 파일명 분리

사용자가 전달한 원본 파일명을 그대로 서버 저장명으로 사용하면 같은 파일명이 중복되거나 경로 조작 문자열이 포함될 수 있다고 판단.

- 원본 파일명에서 \, / 경로를 제거하고 마지막 파일명만 사용
- 원본 파일명은 업로드 이력 확인을 위해 DB에 저장
- 실제 파일은 UUID 기반의 별도 파일명으로 저장
- 저장 경로를 `normalize()`한 후 지정된 업로드 디렉터리 내부인지 재검증
- Docker에서는 `/app/uploads` 전용 볼륨에 저장해 애플리케이션 실행 영역과 분리

이를 통해 원본 파일명 충돌과 `../` 형태의 경로 조작 가능성을 줄이고, 사용자가 입력한 파일명이 실제 서버 경로에 직접 사용되지 않도록 구현.

### 2. 파일명에 따른 확장자 추출 기준 정의

점으로 시작하는 파일이나 이중 확장자를 무조건 허용하거나 차단하지 않고, 파일명의 마지막 점을 기준으로 확장자를 추출하도록 기준 상정.

- `file.PDF`는 소문자로 변환해 `pdf`로 처리
- `file.exe.txt`는 마지막 확장자인 `txt`로 처리
- `.tar.gz`는 마지막 확장자인 `gz`로 처리
- `.env`는 마지막 점 뒤의 `env`를 확장자로 처리
- `.profile.txt`는 `txt` 확장자로 처리해 업로드 허용
- 점이 없거나 파일명이 점으로 끝나면 확장자가 없는 파일로 처리
- 원본 파일명이 255자를 초과하면 업로드 거부

### 3. 클라이언트 상태를 신뢰하지 않는 서버 검증

화면의 체크 상태나 클라이언트 검증은 직접 API를 호출하면 우회할 수 있으므로, 업로드 요청이 들어올 때마다 서버가 DB의 확장자 정책을 다시 조회하도록 구현.

- 업로드 시점의 `extension_policies.blocked` 값을 기준으로 차단 여부 판단
- 클라이언트 요청값과 관계없이 서버에서 확장자 재추출
- 차단된 확장자는 실제 파일로 저장하기 전에 업로드 거부
- 확장자 입력은 공백 제거, 소문자 변환, 앞의 점 제거 후 검증
- 확장자명은 영문 소문자와 숫자만 허용하고 길이는 1~20자로 제한

### 4. DB UNIQUE 제약을 이용한 동시성 방어

커스텀 확장자를 저장하기 전에 중복 여부를 조회하더라도 같은 요청이 동시에 들어오면 두 요청 모두 조회를 통과할 수 있다고 판단.

- 서비스에서 `existsByExtension()`으로 중복 여부를 먼저 확인
- `extension_policies.extension`에 DB UNIQUE 제약 적용
- UNIQUE 제약 위반은 `409 Conflict`로 응답
- 동일한 확장자 추가 요청 10개를 동시에 전송하는 테스트 수행

동시성 테스트 결과는 다음과 같다.

```text
status=200 count=1
status=409 count=9
```

애플리케이션 검증은 빠른 오류 응답을 담당하고, 최종 데이터 중복 방지는 DB가 담당하도록 역할을 나눴다.

### 5. 업로드 성공과 실패 이력 분리 저장

성공한 파일만 저장하면 어떤 파일이 어떤 이유로 거부됐는지 확인하기 어렵다고 판단해 업로드 결과를 `uploaded_files`에 기록하도록 구현했다.

성공한 업로드에는 다음 정보를 저장한다.

- 원본 파일명
- 실제 저장 파일명
- 확장자와 MIME 타입
- 파일 크기와 저장 경로
- `STORED` 상태와 생성 시각

확장자 없음, 차단 확장자, 파일명 길이 초과로 거부된 업로드에는 다음 정보를 저장한다.

- 원본 파일명과 확장자
- MIME 타입과 파일 크기
- `REJECTED` 상태
- 구체적인 거부 사유

거부된 파일은 실제 저장소에 생성하지 않고 DB에 실패 이력만 기록하도록 분리했다.

### 6. 파일 크기 제한과 명확한 오류 응답

대용량 파일이 서버 저장 공간과 네트워크 자원을 과도하게 사용하는 것을 막기 위해 업로드 크기를 제한했다.

- 단일 파일 최대 크기: 10MB
- multipart 요청 전체 최대 크기: 20MB
- 10MB 초과 파일: `413 Payload Too Large`
- 오류 코드: `FILE_SIZE_EXCEEDED`

처음에는 크기 초과 요청이 `500 Internal Server Error`로 반환됐지만, `MaxUploadSizeExceededException`을 공통 예외 처리에 추가해 사용자가 실패 원인을 구분할 수 있도록 수정했다.

### 7. 공통 오류 응답과 실패 원인 구분

모든 실패를 같은 메시지로 처리하지 않고 상황별 오류 코드를 구분했다.

- 잘못된 확장자 형식: `INVALID_EXTENSION`
- 중복 확장자: `EXTENSION_ALREADY_EXISTS`
- 고정 확장자 삭제: `FIXED_EXTENSION_NOT_DELETABLE`
- 차단된 파일 업로드: `BLOCKED_FILE_EXTENSION`
- 확장자 없는 파일: `FILE_EXTENSION_REQUIRED`
- 긴 파일명: `FILENAME_TOO_LONG`
- 파일 크기 초과: `FILE_SIZE_EXCEEDED`
- 파일 저장 실패: `FILE_STORAGE_FAILED`

HTTP 상태, 오류 코드, 메시지, 상세 정보, 발생 시각을 공통 형식으로 반환해 프론트엔드가 오류 종류에 따라 안내할 수 있도록 했다.

### 8. 정책 변경 이력 저장

확장자 정책은 파일 업로드 가능 여부에 직접 영향을 주므로 현재 값뿐 아니라 변경 이력도 확인할 수 있도록 구성했다.

- 커스텀 확장자 추가 이력
- 커스텀 확장자 삭제 이력
- 차단 상태 변경 전후 값
- 변경 대상 확장자와 정책 ID
- 작업자, 변경 사유, 변경 시각

현재 인증 기능이 없는 단일 관리자 구조이므로 작업자는 `system`으로 기록하고, 추후 사용자 정보와 연결할 수 있도록 `actor` 컬럼을 분리.

### 9. 고정 확장자의 삭제 방지와 상태 확장성

고정 확장자 `bat`, `cmd`, `com`, `cpl`, `exe`, `scr`, `js`는 코드 상수로만 관리하지 않고 일반 확장자 정책과 함께 DB 저장.

- `fixed=true`로 고정 확장자 구분
- `blocked` 값으로 차단 상태 관리
- 고정 확장자 삭제 요청은 오류로 거부
- 고정 확장자도 차단 상태는 변경 가능
- 커스텀 확장자와 동일한 조회 API에서 함께 반환

고정 확장자와 커스텀 확장자의 구조를 분리하지 않아 새로운 기본 확장자가 추가되더라도 동일한 정책 구조를 사용할 수 있도록 구성.

### 10. Docker 볼륨을 이용한 데이터 유지

컨테이너가 재생성될 때 DB와 업로드 파일이 함께 사라지지 않도록 저장 영역을 Docker named volume으로 분리.

- MySQL 데이터: `mysql-data:/var/lib/mysql`
- 업로드 파일: `uploads:/app/uploads`
- 애플리케이션 컨테이너와 데이터 저장 수명 분리
- MySQL healthcheck 통과 후 Spring Boot 서버 실행

이를 통해 애플리케이션 이미지를 다시 빌드하거나 컨테이너를 재시작해도 확장자 정책, 업로드 이력, 실제 파일이 유지되도록 구성.
