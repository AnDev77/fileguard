# PROMPT_LOG

실제 개발 대화를 시간 순서에 맞게 정리한 프롬프트 기록이다.  
핵심 정책과 검증 기준은 직접 결정하고, AI는 스켈레톤·반복 코드·테스트 자동화에 활용했다.

## 사용 도구

- Codex: 스켈레톤, 반복 코드, 테스트 스크립트 작성
- Spring Boot / Spring Data JPA: 백엔드 API 구현
- MySQL / Flyway: 데이터 저장과 스키마 관리
- Docker Compose: 애플리케이션과 MySQL 실행
- JUnit / PowerShell / curl: 단위 테스트와 실제 API 검증
- React / Vite / Lucide React: 프론트엔드 구현

---

## 1. 프로젝트 스켈레톤과 실행 환경 구성

### 프롬프트 입력

```text
Java 21, Spring Boot, Maven, MySQL, Flyway, Docker Compose 기반으로
파일 확장자 차단 프로젝트의 초기 스켈레톤 구현.

구성 범위:
- common, extension, upload 패키지 분리
- 공통 성공 응답, 오류 코드, 비즈니스 예외, 전역 예외 처리
- Spring Web, Validation, JPA, MySQL, Flyway 의존성
- DB 접속 정보와 파일 저장 경로를 환경변수로 관리
- Flyway 마이그레이션 기본 구조
- Spring Boot와 MySQL을 함께 실행하는 Docker Compose
- MySQL healthcheck와 애플리케이션 기동 확인 API

비즈니스 로직은 제외하고 이후 기능을 추가할 수 있는 실행 가능한 구조까지 작성.
```

### 프롬프트 의도

반복적인 프로젝트 초기 설정을 빠르게 완료하고, 직접 설계한 기능을 추가할 기반을 마련하기 위함.

### AI 활용 범위

- Maven 의존성, 패키지, 공통 응답·예외 처리, Docker 기본 코드

### 직접 설계·수정·검증한 부분

- 고정·커스텀 확장자를 하나의 `extension_policies` 테이블에서 `fixed`, `blocked` 값으로 구분하도록 설계
- 정책 추가·삭제·상태 변경을 남기는 `policy_change_logs`와 성공·실패 업로드를 남기는 `uploaded_files` 설계
- 확장자 중복 방지를 위한 제약조건과 조회에 필요한 인덱스 결정
- `bat`, `cmd`, `com`, `cpl`, `exe`, `scr`, `js`를 Flyway 초기 데이터로 구성
- JPA가 스키마를 임의 변경하지 않도록 `ddl-auto=validate`를 적용하고 스키마 관리를 Flyway로 분리
- 로컬 MySQL과의 포트 충돌을 확인해 Docker 호스트 포트를 `13306`으로 수정하고 실제 연결 확인

## 2. 과제 최소 기능 구현

### 프롬프트 입력

```text
현재 프로젝트에 파일 확장자 차단 과제의 최소 기능을 REST API로 구현.
아래 기능 기준은 확정된 설계이므로 그대로 반영.

확장자 정책:
- 고정 확장자 bat, cmd, com, cpl, exe, scr, js 조회
- 고정 확장자는 삭제할 수 없고 blocked 상태만 변경
- 커스텀 확장자 추가와 삭제
- 커스텀 확장자 최대 200개, 확장자명 최대 20자
- 고정 확장자와 커스텀 확장자의 중복 등록 거부

파일 업로드:
- multipart/form-data 실제 파일 업로드
- 업로드 시 DB의 확장자 차단 정책 조회
- 차단된 확장자는 저장하지 않고 공통 오류 응답
- 허용된 파일은 서버 저장소에 저장
- 정책 변경은 policy_change_logs에 기록
- 업로드 결과는 uploaded_files에 기록

Entity, Repository, Service, Controller, DTO를 역할별로 분리해 구현.
```

### 프롬프트 의도

과제 명세를 직접 데이터 규칙과 API 동작으로 구체화하고, 반복적인 계층별 코드는 AI로 구현하기 위함.

### AI 활용 범위

- Entity, Repository, DTO와 CRUD·업로드 서비스의 기본 코드

### 직접 설계·수정·검증한 부분

- 고정 확장자는 삭제하지 않고 `blocked` 상태만 변경하며, 삭제 요청에는 전용 오류를 반환하도록 결정
- 커스텀 확장자는 최대 200개, 확장자명은 최대 20자로 제한하고 등록 즉시 차단 정책으로 사용
- 대소문자와 앞쪽 점을 정규화하고 고정·커스텀 확장자의 중복 등록을 거부하도록 설계
- 정책 추가·삭제·상태 변경·고정 확장자 삭제 거부에 남길 로그 종류와 사유 결정
- 공통 오류 코드와 HTTP 상태를 기능별 실패 원인에 맞게 구체화
- 확장자 조회·추가·삭제·상태 변경과 허용·차단 파일 업로드 결과를 API와 DB에서 직접 확인

## 3. 최소 기능 검증과 파일 처리 기준 개선

### 프롬프트 입력

```text
최소 기능을 실제 HTTP 요청으로 검증하고, 검증 과정에서 정한
파일명·확장자 처리 기준을 코드와 테스트에 반영.

검증 자동화:
- 확장자 조회·추가·삭제·상태 변경의 정상 및 실패 요청
- 허용 파일 업로드 성공과 차단 파일 업로드 실패
- HTTP 상태, 오류 코드, DB 이력, 실제 저장 파일 확인
- PowerShell, curl, JUnit 기반 반복 테스트

파일 처리 기준:
- 원본 파일명은 DB에 기록하고 실제 파일은 UUID 이름으로 저장
- 확장자는 마지막 점 뒤 문자열을 소문자로 변환해 사용
- .env는 env, .profile.txt는 txt, file.exe.txt는 txt로 처리
- 점이 없거나 마지막 문자가 점이면 확장자 없음으로 처리
- 원본 파일명은 최대 255자
- 저장 경로 normalize 후 업로드 디렉터리 내부인지 확인
- 업로드 시 서버에서 최신 차단 정책을 다시 조회
- 성공은 STORED, 차단·검증 실패는 REJECTED와 사유로 기록
```

### 프롬프트 의도

최소 기능을 그대로 신뢰하지 않고 실제 요청으로 검증한 뒤, 발견한 파일 처리 문제를 기준화해 반복 개선하기 위함.

### AI 활용 범위

- PowerShell/curl 테스트 구조, 확장자 추출 유틸리티, UUID 저장 코드

### 직접 설계·수정·검증한 부분

- 원본 파일명은 조회용으로 DB에 보관하고 실제 파일은 UUID 이름으로 저장해 충돌과 경로 조작 위험을 분리
- 확장자는 마지막 점 뒤 문자열로 판단하고 소문자로 정규화하도록 기준 결정
- `.env`는 `env`, `.profile.txt`는 `txt`, `file.exe.txt`는 `txt`, `.tar.gz`는 `gz`로 처리
- 점이 없거나 마지막 문자가 점인 파일은 확장자 없음으로 거부하고 원본 파일명은 255자로 제한
- 프론트엔드 검증을 신뢰하지 않고 업로드 시 서버가 최신 DB 차단 정책을 다시 조회하도록 적용
- 차단 예외와 함께 `REJECTED` 이력이 롤백되는 문제를 수정하고 DB 이력과 실제 UUID 파일을 함께 검증

## 4. DB 제약조건을 이용한 동시성 처리

### 프롬프트 입력

```text
커스텀 확장자 등록의 사전 중복 조회만으로는 동시 요청을 막을 수 없으므로
DB 제약조건을 최종 방어로 사용하는 방식으로 보완.

- extension_policies.extension에 UNIQUE 제약조건 적용
- 애플리케이션의 사전 중복 검사는 빠른 오류 응답을 위해 유지
- DB 제약 위반을 공통 오류 응답으로 변환
- 동일한 확장자 추가 요청 10개를 동시에 실행
- 각 요청의 HTTP 상태와 오류 코드 출력
- 테스트 후 DB의 동일 확장자 저장 개수 확인

Flyway 변경, 예외 처리, PowerShell 병렬 테스트 코드 작성.
```

### 프롬프트 의도

조회 후 저장 과정의 경쟁 조건을 직접 식별하고, DB 무결성 제약과 실제 동시 요청으로 해결 방식을 검증하기 위함.

### AI 활용 범위

- `UNIQUE` 마이그레이션, 데이터 무결성 예외 처리, 병렬 요청 코드

### 직접 설계·수정·검증한 부분

- 사전 중복 조회만으로는 동시에 들어온 요청이 모두 조회를 통과할 수 있음을 경쟁 조건으로 판단
- 빠른 오류 응답을 위한 서비스 중복 검사는 유지하고 DB `UNIQUE`를 최종 방어로 결정
- `DataIntegrityViolationException`이 일반 `500`으로 반환되지 않도록 `409 Conflict`로 변환
- 동일 확장자 10건을 병렬 요청해 성공 1건, 실패 9건, DB 저장 1건을 직접 확인

## 5. 백엔드 안정화와 다운로드 기능 완성

### 프롬프트 입력

```text
파일 업로드 백엔드의 경계값 처리와 다운로드 기능을 완성.
아래 기준은 검증을 위해 결정한 값이므로 그대로 적용.

파일 크기와 저장:
- 단일 파일 최대 10MB
- multipart 요청 전체 최대 20MB
- 크기 초과 시 413 Payload Too Large와 FILE_SIZE_EXCEEDED 반환
- MySQL 데이터와 업로드 디렉터리에 Docker named volume 적용
- 1MB 파일 성공과 11MB 파일 실패 테스트 작성

다운로드:
- STORED 상태의 업로드 파일 목록 조회 API
- 파일 ID를 이용한 다운로드 API
- 저장 경로 내부의 실제 파일 존재 여부 재검증
- Content-Type과 Content-Disposition 응답 헤더 적용
- 사용자가 업로드한 원본 파일명으로 다운로드

실제 업로드·조회·다운로드와 파일 해시 비교 테스트 작성.
```

### 프롬프트 의도

서버 자원 제한과 데이터 유지 기준을 명확히 하고, 저장된 파일을 안전하게 다시 제공하는 백엔드 흐름을 완성하기 위함.

### AI 활용 범위

- multipart 설정, 크기 테스트 파일 생성, 다운로드 응답 기본 코드

### 직접 설계·수정·검증한 부분

- 서버 자원 사용을 고려해 단일 파일 10MB와 multipart 전체 요청 20MB를 서로 다른 제한값으로 결정
- 컨트롤러 진입 전에 발생한 크기 초과 예외가 `500`으로 반환되는 문제를 `413`과 전용 오류 코드로 수정
- 1MB 파일 성공과 11MB 파일 실패를 실제 HTTP 요청으로 확인
- 컨테이너 재생성 후에도 DB와 파일이 유지되도록 MySQL과 업로드 경로에 named volume 적용
- 다운로드는 `STORED` 상태만 허용하고 저장 경로와 실제 파일 존재 여부를 다시 확인하도록 설계
- 원본 파일명으로 다운로드한 파일의 SHA-256이 업로드 원본과 일치하는지 검증

## 6. React 프론트엔드 구현과 통합 검증

### 프롬프트 입력

```text
완성된 Spring Boot API만 사용해 React/Vite 프론트엔드 구현.
백엔드 코드는 변경하지 않고 화면과 API 연동만 작업.

화면 구성:
- 고정 확장자와 커스텀 확장자 관리 영역 분리
- 고정 확장자는 체크박스로 차단 상태 변경
- 커스텀 확장자 입력, 추가, 목록 조회, 삭제
- 파일 선택과 실제 업로드
- 업로드 성공 파일 목록과 다운로드

UX:
- 추가·삭제·상태 변경·업로드 결과를 화면 알림으로 표시
- 차단 확장자명과 차단 사유 표시
- 로딩, 요청 중, 네트워크 실패 상태 처리
- API 처리 후 서버 데이터를 다시 조회
- 새로고침 후 DB 상태 유지
- 다른 브라우저 세션의 변경사항 동기화
- 데스크톱과 모바일 반응형 구성

API 호출은 별도 모듈로 분리하고 다운로드 응답은 Blob으로 처리.
```

### 프롬프트 의도

완성된 백엔드 계약을 기준으로 프론트엔드를 독립적으로 구현하고, 화면 상태와 실제 DB 상태의 일관성을 검증하기 위함.

### AI 활용 범위

- React 컴포넌트, API 모듈, Blob 다운로드, 알림·로딩 기본 코드

### 직접 설계·수정·검증한 부분

- 고정 확장자, 커스텀 확장자, 파일 업로드, 파일 목록을 작업 흐름에 맞게 화면 영역으로 분리
- 기본 `alert` 대신 추가·삭제·차단·업로드 결과와 실패 원인을 구분하는 화면 알림 적용
- 브라우저 상태만 변경하지 않고 API 처리 후 서버 데이터를 다시 조회해 DB와 화면 상태를 일치
- 다른 세션 변경을 반영하기 위해 주기 조회, 화면 포커스 복귀, 수동 새로고침 방식 적용
- 다운로드 응답을 Blob으로 처리하고 사용자가 업로드한 원본 파일명으로 저장
- 확장자 관리, 허용·차단 업로드, 다운로드, 새로고침, 다른 세션 동기화를 화면에서 직접 검증
